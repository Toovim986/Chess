# Цикл сборки и проверки

## До сборки

Выполнить `node cli.mjs context chess`. Прочитать activeRules, релевантные lessons и профиль. Через Figma проверить точные узлы DS и их текущие варианты. Для задачи зафиксировать цель, состояния, переходы, содержимое, платформу, композиционный эталон или утверждённое описание композиции и место сдачи.

В `project.json` ссылки designSystem/productContract/compositionContract имеют revision, reviewedBy, verifiedAt, evidencePath и sha256. Для Figma указаны fileKey/nodeId; для Google Docs — `kind: "google-docs"` и documentId. Локальный файл доказательства расположен внутри профиля. Частичный ГДД с `completeness: "partial"` фиксирует источник, но сохраняет PRODUCT_GAP по открытым требованиям. Для нового mobile-first сценария compositionContract может ссылаться на отдельную утверждённую карточку/фрейм композиции в Figma; desktop-копия не обязательна. destination задаётся fileKey/pageId, viewportPolicy — version и sizes: [{width,height}].

Preflight проверяет структуру и хеш локальных ссылок. Агент отдельно сверяет содержание и актуальность. Для каждого состояния составляется небольшой контракт: компоненты/варианты DS; допустимые изменения; читаемые данные; действия и переходы; критические bounds; обязательные проверки и их владельцы.

## Во время сборки

Собрать отдельную ревизию средствами Figma. Подключать нативные экземпляры библиотеки. Неизвестное правило оформить как DESIGN_GAP или кандидата на паттерн. Продуктовое поведение без источника оформить как PRODUCT_GAP. Изменение детального компонента или исключение оформить решением с конкретным scope.

Инструмент сам не вызывает Figma и не строит экраны. Агент использует доступный Figma MCP с его актуальными инструкциями; `engine/figma-capture.js` — исходный read-only сборщик снимков, который исполняется в контексте Figma через предусмотренный инструмент.

## Проверка

Проверка исходника сравнивает равномерно масштабируемые поддеревья. Сетка проверяет измеримые координаты и отступы в согласованном режиме. Применимость сетки и округлений указывается явно. Эти проверки не заменяют DS bindings, варианты, стили всех диапазонов текста, визуальное ревью, покрытие сценариев и реальное приложение.

Проверки DS, композиции, состояний, визуального ревью и runtime фиксируются отдельными результатами с областью проверки и артефактами. Для шахмат автоматического viewport-правила пока нет. При отсутствии runtime-измерений соответствующий результат остаётся INCOMPLETE.

## Сохранение результата

Положить финальные PNG и отчёты в `profiles/<profile>/incoming/`. Через API импортировать новую ревизию с точными source/target fileKey/pageId, списком экранов и sourceIds, проверками, findings, измерениями до/после и parentAuditId для исправлений. Формат — `RUNTIME.md`.

Проверить сохранённый manifest, скачать каждый артефакт, сверить SHA-256 и размеры PNG. Проверить галерею и восстановление после перезагрузки. Записать результат сохранения отдельно от статуса дизайна. Исходные FAIL/INCOMPLETE сохраняются, даже если импорт выполнен успешно.

Для обсуждения сдать изображение с известными ограничениями. Для вёрстки дополнительно нужен утверждённый набор состояний, переходов, источников компонентов и незакрытых решений. Назначенный владелец подтверждает готовность.

## Пополнение знаний

Новый урок: ID, scope, проблема, исправление, точный документ/аудит и Figma fileKey/nodeId. Кандидат на правило дополнительно имеет владельца, условия применения, исключения и проверку. До утверждения он сохраняет candidate. Новая версия DS не переписывает прежний результат; для затронутых экранов создаётся новая проверка/ревизия.
